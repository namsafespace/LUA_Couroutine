CCS 2105 - IMPORTANT COROUTINE CONCEPTS
============================================

1. COROUTINE
------------
A coroutine is a function that can pause its execution and later
continue from the same point.

Unlike a normal function, it does not have to finish in one run.


2. PERSISTENT EXECUTION STATE
-----------------------------
When yield() pauses a coroutine, Lua preserves its execution state.

Local variables and the current position in the function are retained.

When resume() is called, execution continues from where yield()
stopped.


3. COOPERATIVE CONCURRENCY
--------------------------
Coroutines voluntarily give up control by calling yield().

The scheduler decides which coroutine to resume next.

The coroutine itself is responsible for yielding.


4. QUASI-CONCURRENCY / INTERLEAVING
-----------------------------------
Several coroutines can appear to run at the same time because their
execution is interleaved.

Example:

Task A -> yield
Task B -> yield
Task C -> yield
Task A -> yield

Only one coroutine is executing at a time.


5. NOT TRUE PARALLELISM
-----------------------
Lua coroutines do not normally execute simultaneously on multiple
CPU cores.

For true parallel execution, threads or processes are more suitable.


6. SCHEDULER
------------
A scheduler controls which coroutine runs next.

A scheduler commonly:
- checks coroutine status
- selects an active coroutine
- calls resume()
- receives yielded information
- repeats until all tasks finish


7. ROUND-ROBIN SCHEDULING
-------------------------
Each active coroutine receives a turn in order.

Example:

A -> B -> C -> D -> A -> B -> C -> D

Advantage:
Fair and simple.

Disadvantage:
Does not consider task importance.


8. PRIORITY SCHEDULING
----------------------
Coroutines with higher priority receive more turns.

Example:

High priority -> 3 turns
Medium priority -> 2 turns
Low priority -> 1 turn

Advantage:
Important work progresses faster.

Disadvantage:
A poorly designed priority system can cause starvation.


9. FAIRNESS
-----------
Fairness means every eligible coroutine eventually receives execution
time.

A scheduler should avoid allowing one busy task to dominate the system.


10. STARVATION
-------------
Starvation occurs when a coroutine waits indefinitely because other
coroutines are always selected first.

A common solution is AGING.

AGING:
Increase a task's priority as its waiting time increases.


11. RESOURCE ALLOCATION
-----------------------
Some exercises involve limited resources such as:
- emergency resources
- storage capacity
- stock
- water
- boarding capacity

The scheduler must check availability before assigning resources.


12. CONDITIONAL SUSPENSION
--------------------------
A coroutine may pause when it cannot continue.

Example:
- waiting for security clearance
- waiting for manual approval
- waiting for network recovery
- waiting for resources

Other coroutines can continue while it is suspended.


13. RETRY
---------
A temporarily failed task can be suspended and retried later.

A retry limit should be used.

Example:

if retries < MAX_RETRIES then
    retry
else
    terminate
end

This prevents infinite retry loops.


14. TERMINATION
---------------
A coroutine becomes "dead" after its function finishes or terminates
because of an error.

A scheduler should remove or skip dead coroutines.


15. ERROR HANDLING
------------------
coroutine.resume() returns:

true, results...

when successful.

It returns:

false, error_message

when the coroutine fails.

The scheduler can handle the error without necessarily stopping every
other coroutine.


16. PIPELINE PROCESSING
----------------------
A workflow can be divided into stages.

Example:

Receiving
-> Weighing
-> Withering
-> Drying
-> Grading
-> Packaging

A coroutine can yield after each stage.


17. PRODUCER-CONSUMER
---------------------
A producer creates items while a consumer receives and processes them.

yield() can allow the producer to pause after producing one item.


18. TWO-WAY COMMUNICATION
-------------------------
Communication can happen in both directions.

Coroutine -> Scheduler:
yield(status, data)

Scheduler -> Coroutine:
resume(coroutine, decision)


19. STATE ISOLATION
-------------------
Each coroutine should maintain its own state.

For example, each student's registration state or each emergency's
current stage should be stored separately.

This prevents one workflow from overwriting another workflow's state.


20. FAIRNESS VS THROUGHPUT
--------------------------
There is often a trade-off.

Serving the largest or highest-priority workload may increase
throughput.

Giving every task regular turns improves fairness.

A good scheduler balances both.


21. COOPERATIVE VS PRE-EMPTIVE
------------------------------
COOPERATIVE:
- Task voluntarily yields.
- Scheduler chooses the next task.
- Simple state management.
- A task that never yields can block others.

PRE-EMPTIVE:
- System can interrupt a running task.
- Usually associated with threads/processes and operating-system
  scheduling.
- Better for workloads requiring stronger isolation or true
  parallelism.


22. KEY STATUS CHECK
--------------------
Before resuming:

if coroutine.status(co) ~= "dead" then
    coroutine.resume(co)
end

This prevents attempts to resume completed coroutines.


23. GENERAL COROUTINE WORKFLOW
-----------------------------

Create
   |
   v
Resume
   |
   v
Execute
   |
   v
Yield
   |
   v
Scheduler chooses another task
   |
   v
Resume again
   |
   v
Continue from saved state
   |
   v
Finish
   |
   v
Dead


24. MAIN LESSON FROM THE ASSIGNMENT
-----------------------------------
The exercises are not mainly about writing complicated Lua programs.

They test whether you can use coroutines to model:

- independent workflows
- persistent state
- interleaved execution
- scheduling
- fairness
- priority
- suspension and resumption
- resource constraints
- error handling
- termination
- two-way communication

The central pattern is:

CREATE -> RESUME -> YIELD -> SCHEDULE -> RESUME -> ... -> DEAD
